1. ARQUITECTURA GENERAL Y FLUJO DEL PROYECTO
--------------------------------------------------------------------------------
El ERP Escolar es un sistema monolítico modular desarrollado en Python 3.12 y
Django 6.0+, respaldado por una base de datos PostgreSQL 16, dockerizado 
completamente para su despliegue y desarrollo local.

Principios Fundamentales del Sistema:
1. Eliminación Lógica (Soft Delete):
   Ningún registro operativo se borra físicamente de la base de datos.
   Todos los modelos heredan de ModeloAuditable (APPS/core/models.py) y emplean
   ActivosManager como manager por defecto (objects), el cual filtra automáticamente
   esta_eliminado=False en todas las consultas.
   Para consultas de auditoría completa, se expone el manager secundario 'todos'.

2. Integridad Referencial Estricta (models.RESTRICT):
   Para prevenir inconsistencias o pérdidas accidentales, las llaves foráneas usan
   on_delete=models.RESTRICT. Al intentar eliminar lógicamente un registro padre
   (ej. Grado, Personal o Usuario), el método ModeloAuditable.delete() verifica mediante
   introspección si existen hijos no eliminados. Si los hay, eleva RestrictedError y
   bloquea la operación.

3. Auditoría e Historial Inmutable:
   Se integra django-simple-history en modelos críticos (NotaBloque en academico,
   PagoColegiatura en financiero y ArticuloInventario en inventario) para registrar el
   historial completo de cambios (versiones), el usuario responsable y el timestamp.


2. FUNCIONAMIENTO DEL SISTEMA DE AUTENTICACIÓN (LOGIN / LOGOUT)
--------------------------------------------------------------------------------
El subsistema de inicio y cierre de sesión se apoya en django.contrib.auth utilizando
el modelo de usuario personalizado Usuario (AUTH_USER_MODEL = 'usuarios.Usuario').

Flujo de Login y Redirecciones:
- Formulario de Inicio de Sesión: Renderizado mediante la plantilla usuarios/login.html
  usando la vista nativa LoginView de Django. Los campos están estilizados con Tailwind CSS v4.
- Redirecciones Automáticas (IBACOOP_PROGRESO/settings.py):
  * LOGIN_URL = 'usuarios:login' -> Redirige a los usuarios anónimos al intentar acceder a rutas protegidas.
  * LOGIN_REDIRECT_URL = 'core:home' -> Redirige al Dashboard principal tras autenticarse exitosamente.
  * LOGOUT_REDIRECT_URL = 'usuarios:login' -> Redirige a la pantalla de login al cerrar sesión.
- Parámetro redirect_authenticated_user=True:
  Si un usuario que ya tiene sesión activa intenta acceder a /usuarios/login/, el sistema lo
  reenvía automáticamente al Dashboard principal.
- Protección de Vistas:
  Todas las vistas del sistema (como HomeView en APPS/core/views.py) requieren sesión activa mediante
  el mixin LoginRequiredMixin.


3. FUNCIONAMIENTO DE LA GESTIÓN DE USUARIOS Y PERMISOS DE SEGURIDAD
--------------------------------------------------------------------------------
El sistema aplica una regla estricta de separación entre la interfaz visual (UI) y
la autorización en backend:

[REGLA CRÍTICA DE SEGURIDAD]
- Campo 'rol' (RolChoices):
  Define la función institucional (ADMINISTRADOR, DIRECTOR, SECRETARIA, CONTADOR, DOCENTE,
  ESTUDIANTE, ENCARGADO). Este campo se usa EXCLUSIVAMENTE en las plantillas HTML (templates)
  para adaptar la interfaz del usuario: mostrar menús laterales dinámicos, insignias de rol o
  tarjetas de resumen en el Dashboard. NO otorga ni limita permisos en el servidor.
- Permisos Reales en Backend:
  La autorización se gestiona obligatoriamente mediante los Grupos (Groups) y Permisos
  nativos de Django. Las vistas validan el acceso con PermissionRequiredMixin.

Formularios e Interfaz de Usuarios:
- CustomUserCreationForm y CustomUserChangeForm (APPS/usuarios/forms.py) heredan de
  TailwindFormMixin para inyectar el diseño institucional en los inputs.
- Permiten gestionar nombre de usuario, datos personales, correo, rol visual, bandera
  ¿Usuario Activo? (is_active) y la asignación múltiple de Grupos de Permisos.

Vistas CRUD de Gestión de Usuarios (APPS/usuarios/views.py):
- UsuarioListView:
  Exige el permiso 'usuarios.view_usuario'. Muestra el listado paginado (10 elementos por página)
  optimizado con prefetch_related('groups') para evitar el problema de consultas N+1.
- UsuarioCreateView:
  Exige el permiso 'usuarios.add_usuario'. Permite registrar usuarios y notifica con
  SuccessMessageMixin.
- UsuarioUpdateView:
  Exige el permiso 'usuarios.change_usuario'. Permite editar la información de un usuario existente.
- Manejo de Denegación de Acceso:
  Todas las vistas de gestión tienen raise_exception = True, devolviendo una respuesta HTTP 403
  Forbidden cuando un usuario autenticado intenta realizar una acción para la cual su usuario
  no posee el permiso nativo requerido.

Vinculación con Perfiles Institucionales:
- Las entidades principales del colegio poseen su cuenta de acceso mediante una relación de uno a uno:
  * Estudiante -> usuario = OneToOneField(Usuario, RESTRICT)
  * Personal (Docentes / Administrativos) -> usuario = OneToOneField(Usuario, RESTRICT)
  * Encargado -> usuario = OneToOneField(Usuario, RESTRICT, null=True)
